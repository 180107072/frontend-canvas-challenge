# Канвас на React Flow — решение

Редактор цепочек «текст → генератор → результат» на React 19, TypeScript, Vite, Tailwind 4,
`@xyflow/react`, TanStack Query, Zustand и shadcn/ui.

## Запуск

Node.js 24.x, npm 11.x. Зависимости зафиксированы общим `package-lock.json` в корне.

```sh
npm ci                # из корня репозитория
npm run dev           # терминал 1: API на http://localhost:4001
npm run dev:web       # терминал 2: фронтенд на http://localhost:5173

npm run build:web           # tsc -b && vite build
npm run test -w @canvas/web # 28 проверок, node:test

# tsc -b проверяет и src, и test: тесты собраны отдельным проектом
# (tsconfig.test.json), поэтому фикстуры типизированы и не прячут ошибок за as.
```

Адрес API задаётся через `VITE_API_URL` (`apps/web/.env.example`).

## Как устроен код

Поток данных односторонний: `api/client` → `api/endpoints` → `api/queries` → компонент.
React-обвязка вынесена в `providers/`, поэтому остальные модули — обычные `.ts` без JSX.

| Файл                  | Ответственность                                                          |
| --------------------- | ------------------------------------------------------------------------ |
| `api/client.ts`       | Исполнитель запросов: единственное место, где вызывается `fetch`         |
| `api/endpoints.ts`    | Дескрипторы: путь, метод, тело, свои заголовки, чтение ответа            |
| `api/queries.ts`      | Политика повторов, устаревания и опроса; ключи кэша                      |
| `model.ts`            | Правила графа и все чистые преобразования данных                         |
| `store.ts`            | Стор на пространство и стор сессии (Zustand + persist)                   |
| `providers/`          | Контекст стора (`useGraph`) и сохранение: очередь, конфликты, черновик   |
| `generations.ts`      | Запуск генерации и сведение списка запусков                              |
| `lib/`                | Очередь с debounce (без React) и запись черновика окном в `localStorage` |
| `save-status.ts`      | Таблица состояний сохранения: условие, тон, иконка, текст                |
| `nodes.tsx`, `ui.tsx` | Три типа нод поверх одной оболочки; общие поле, кнопка, вывод ошибки     |
| `components/`         | Опрос активных генераций (`tracker`) и примитивы shadcn/ui               |

### Запросы

Эндпоинт — это **данные**, а не функция: дескриптор объявляет только то, чем запрос отличается.

```ts
saveGraph: {
  method: 'PUT',
  path: ({ spaceId }) => `/api/spaces/${spaceId}/graph`,
  body: ({ graph }) => graph,
  headers: ({ etag }) => ({ 'If-Match': etag }),
  read: readGraph,
}
```

Всё общее — адрес, `Content-Type`, сериализация, проверка статуса, пустые ответы, разбор JSON и
приведение любой ошибки к `RequestError` (`kind`, `code`, `status`, `message`, `retriable`) — живёт
в `createClient()`, поэтому четыре стадии меняются независимо. `fetch` внедряется
(`createClient({ fetch })`), и исполнитель покрыт юнит-тестами. Компоненты не видят `Response`:
только типизированные данные либо разобранную ошибку, которую показывает общий `ErrorNote`.

Что стоит повторять, решает одно правило `retryPolicy` (сеть или 5xx, не больше двух раз, задержка
вдвое): им настроены и все запросы через `queryClient`, и мутация запуска генерации — ошибка самого
приложения в цикл повторов не уходит.

### Сохранение

Изменение, которое надо сохранить, увеличивает `revision.current`; выделение и замеры размеров ноды
— нет, иначе клик по ноде давал бы лишний PUT. `revision.saved` — значение на момент последнего
принятого PUT.

`lib/save-queue.ts` держит и таймер, и порядок: всё идёт по одной цепочке промисов, поэтому
сохранения не накладываются, а запуск генерации встаёт в ту же цепочку — отдельный флаг «придержать
сохранения» не нужен.

```ts
run(task) {
  stop();                       // снять отложенный debounce
  return enqueue(async () => {
    await save();               // ...и задача — одна запись в очереди,
    return task();              // между ними ничего не вклинится
  });
}
```

Тело собирается внутри мутации, в момент старта, поэтому уходит самое свежее состояние. Из ответа
PUT берётся только `ETag`, а `commit()` помечает сохранённой отправленную ревизию — поздний ответ не
затирает более новые правки.

- **412** — черновик остаётся на экране и в `localStorage`, показан конфликт и «Перечитать граф».
- **Потерянный ответ PUT** — граф перечитывается и сравнивается с отправленным телом; если сервер
  уже применил запись, берётся её `ETag`.
- **Повтор генерации** — при транспортной ошибке прежний `Idempotency-Key`, для нового запуска новый.
- **Пространство исчезло** — ошибка чтения графа показана с кнопкой возврата к списку.

### Черновик

Стор создаётся на каждое пространство, и строка в `localStorage` своя (`canvas:draft:<spaceId>`):
общий стор пришлось бы обнулять при переключении, а единственная строка вмещала бы один черновик.
Что делать с черновиком, когда пришёл граф сервера, решает чистая функция `reconcile`:

| черновик   | версия     | решение                                                  |
| ---------- | ---------- | -------------------------------------------------------- |
| без правок | совпадает  | `keep` — не выбрасывать клиентские поля своей же версией |
| без правок | отличается | `adopt`                                                  |
| с правками | совпадает  | `save`                                                   |
| с правками | отличается | `conflict`                                               |

### Канвас и генерации

`nodeOrigin={[0.5, 0.5]}` — позиция означает центр ноды, поэтому добавление в центр канваса не
требует знать её размер. Viewport управляемый: `onViewportChange` пишет в стор каждый кадр, а
`revision` двигается один раз в `onMoveEnd`. Плата — запись на каждый кадр, поэтому черновик идёт
через окно в 200 мс: 60 кадров панорамирования дают 3 записи (~3.6 КБ) вместо 60 (~72 КБ).

Удаление ноды идёт только через `deleteElements`, поэтому связи уносятся одной реализацией — и с
кнопки, и с клавиши Delete.

Список генераций — единственный источник правды. На каждую незавершённую `useQueries` монтирует
запрос с `refetchInterval`, который останавливается сам. Результат появляется в ноде только если её
текущая входящая связь идёт от того же генератора, который его произвёл.

### Одинаковые правила — одна реализация

- `canConnect` спрашивают `isValidConnection`, `onConnect`, proximity-подключение и кнопка запуска.
- `KINDS[kind].saved` задаёт и состав payload, и то, какая правка стоит PUT; `setValue` — один путь
  записи и для текста, и для сценария.
- `SAVE_RULES` — одна таблица: условие, тон, иконка, текст. `SaveStatus` выведен из неё, поэтому
  состояние не может появиться без условия, а `TONE_CLASS` переводит тон в класс сразу для всех
  подписей — и в нодах, и в нижней панели.
- Лимит графа приходит из `/api/config` (`maxNodes`): один `useNodeLimit` и выключает кнопки
  добавления, и объясняет, что делать. Схема сервера обрывает граф на 21-й ноде (`maxItems: 20`,
  ответ `400 VALIDATION_ERROR`), а такой PUT не проходил бы и после «Повторить».
- `withDefaults` дополняет `data` ноды умолчаниями её типа — и для графа с сервера, и для черновика
  из `localStorage` (через `merge` у `persist`). Умолчание объявлено только в
  `KINDS[kind].create()`, поэтому поле не бывает пустым и `scenario` необязательным не объявлен.

## Разбор одного участка обработки

`indexOf(nodes, edges)` в `model.ts` вызывается при каждом рендере канваса и каждой ноды — во время
перетаскивания десятки раз в секунду. Наивный вариант отвечал бы на каждый вопрос («есть ли вход»,
«какой результат у генератора», «можно ли соединить») отдельным `find`/`filter`, то есть линейным
поиском внутри обхода.

Вместо этого строится один индекс: проход по `nodes` → `Map` «id → нода»; проход по `edges` → `Map`
«цель → входящая связь» и `Map` «генератор → нода результата». Два линейных прохода, три `Map`, ни
одного промежуточного массива; дальше `canConnect` и `chainOf` отвечают за O(1). Результат
мемоизируется в `WeakMap` по идентичности `nodes` с проверкой идентичности `edges`: индекс строится
один раз на изменение графа и его делят все ноды разом, а не пересобирают на каждое обращение.
Панорамирование, зум, статус сохранения и опрос генераций массивов не трогают и переиспользуют
готовый индекс; выделение ноды `applyNodeChanges` возвращает новым массивом, поэтому там индекс
собирается заново — O(n) при n не больше лимита нод.

Похожее в `collectRuns`: за один проход по списку генераций строятся оба индекса и список активных
опросов — вместо `filter().map()` с тремя проходами и двумя временными массивами. Он тоже
мемоизирован `WeakMap` по списку, поэтому восемь нод получают один общий разбор, а не восемь своих.
`replaceById` возвращает прежний массив, если элемент не изменился.

Контекст синхронизации разделён на «действия» (стабильные) и «состояние сохранения» (меняется
несколько раз за сохранение): замер на восьми генераторах — 64 рендера за цикл против 16.

## Что проверено

Юнит-тесты (28): правила связей и цепочки, мемоизация индекса графа и списка генераций, умолчания
полей ноды, состав payload, `reconcile`, сведение генераций; очередь сохранений (один PUT на серию,
отсутствие наложений, `run()` не запускает задачу при неудачном сохранении); исполнитель запросов
(дескриптор → запрос, `read`, доменные ошибки, `retriable`, отмена, пустые тела).

Прогоны в Chromium против реального API:

- пространство создаётся и открывается; три типа нод, перетаскивание, удаление вместе со связями и
  с кнопки, и с клавиши Delete; после перезагрузки открывается то же пространство;
- связи тянутся между портами, `текст → результат` и второй вход отклоняются; proximity-подключение
  идёт по тому же `canConnect`; нода добавляется в центр при высотах 169/189/219 px;
- 8 быстрых нажатий дают один PUT, одиночная правка тоже сохраняется; при медленном PUT (1.2 с) три
  волны правок ушли тремя последовательными запросами без наложения;
- правка и сразу «Сгенерировать» — генерация запустилась с только что сохранённым текстом; успех
  даёт картинку в связанной ноде, отказ — `SIMULATED_FAILURE` и повтор; двойной клик создаёт одну;
- перезагрузка во время генерации — отслеживание продолжилось, после завершения опрос прекратился;
- правка другим клиентом → 412: черновик сохранён, генерация не запускается, «Перечитать граф»
  возвращает серверную версию; конфликтный черновик переживает переход в другое пространство;
- переподключение генератора к другой ноде результата не переносит туда старую картинку;
- черновик, записанный сборкой без поля `scenario`, после перезагрузки открывается с умолчанием, а
  не с пустым контролом;
- 21-я нода не добавляется: кнопки выключены, показано «Достигнут лимит графа: 20 нод», PUT
  остаётся 200; после удаления ноды добавление снова доступно;
- канвас едет за курсором во время панорамирования; смена статуса сохранения не сдвигает нижнюю
  панель (замер: 0.00 px).

## Недоработки

- Сценарий генератора хранится только локально: серверная схема ноды такого поля не имеет.
- Миграции формата черновика (`version`/`migrate` у `persist`) нет: строка от сборки с другим
  составом полей восстановится как есть. На свежем клоне недостижимо.
- При закрытии вкладки черновик не досылается — уходит при следующем открытии пространства.
- Конфликт 412 разрешается только полным перечитыванием; слияния версий нет.
- Правка и её отмена до debounce всё равно дают один PUT: признак «изменено» — счётчик ревизий, а
  не сравнение содержимого.
- Лимит связей (`maxEdges: 20`) отдельно не проверяется: при «один вход на ноду» и не более
  20 нод число связей до него не доходит.
- Мобильная вёрстка не делалась, минимальная ширина макета — 1280 пикселей.
